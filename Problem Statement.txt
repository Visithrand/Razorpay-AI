Problem Statement :

Merchants reconciling payment gateway settlements against bank statements and internal ledgers still do it by hand — three sources, three formats, three timings, no unified source of truth. This creates delayed financial close, hidden revenue leakage, and "where's my money" support tickets that eat merchant trust. We built an agent that auto-matches transactions across all three sources (including hard cases like batched settlements and timing drift), reports an honest match rate with a categorized exception list, and lets anyone ask it plain-English questions about any transaction instead of digging through spreadsheets.


High impact, low effort (do these)
Confidence score per match, not just matched/unmatched. Fuzzy matches get a score (e.g. 0.92) so the human knows which "matches" to double-check. Signals mature engineering, not just binary pass/fail.
Explain-my-decision on every match, not just exceptions. Click any matched row → "matched because UTR exact + amount exact + date within 1 day." Turns your matcher into an auditable system, which is exactly the "explainable, bounded, gated" language they used for Track 1's bar — reuse it here too.
A "confidence threshold" slider — user can tighten/loosen fuzzy-match tolerance and watch match rate + exception count change live. Cheap to build (just a parameter), very demoable, shows you understand the precision/recall tradeoff.

Build order
Data + schema first, always. Write generate_synthetic.py before any matching logic. Seed it (random.seed(42)) so results are reproducible — a reviewer re-running your repo should get the same match rate you quote in your pitch. Generate the clean cases first, then deliberately inject each failure type (fee-adjusted, timing drift, batch, missing, duplicate, amount typo) as labeled test fixtures — you'll reuse these exact rows as your test suite's "known answers."
Matching engine, test-driven. Write test_matcher.py before the matcher, using your labeled fixtures: "this settlement+ledger pair should match with confidence > 0.9 and reason = fee-adjusted." Then write the matcher to pass those tests. This is the single highest-leverage thing you can do — a matcher with a real test suite reads as engineering, not a script that happened to work on your demo run.
Batch unbundler. Your hardest, most differentiating feature. Get this working and tested before touching the LLM layer.
NL2SQL agent. Reuse your FloatChat prompt-engineering approach: schema-grounded prompt, generate SQL, execute against a read-only connection first to validate it doesn't error, then answer. This validate-before-answer step is literally your failure-story fix from FloatChat — build it in from the start this time instead of discovering it live.
API + frontend. FastAPI routes for: upload, get match results, get exceptions, ask question. React dashboard: match rate card, exception table (filterable by category), chat panel. Don't over-design the UI — clean and functional beats fancy.
Docker Compose. One docker-compose up should run the whole thing. A reviewer who has to manually set up Postgres, install deps, and configure env vars in the right order will bounce off your repo in 2 minutes. This single thing matters more than almost any feature.
Metrics, logging, polish. Add structured logging (not print statements) around the matcher and agent. Compute and log match rate + exception breakdown as an actual JSON report artifact (reports/run_2026-08-23.json) — something you can screenshot for the pitch and that proves the number isn't cherry-picked.
